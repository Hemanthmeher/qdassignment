SESSION 3: DETERMINISTIC POLICY ENGINE & MATHEMATICAL SPECIFICATIONS
--------------------------------------------------------------------------------

[ENGINEER QUERY]
"How does the policy engine deterministically audit rider claims without relying on probabilistic LLM math? Explain the mathematical fare formula, calendar window calculation, daily incentive logic, cancellation penalty reconciliation, and the specific data anomaly handling for trip T312538."

[ANTIGRAVITY RESPONSE]
"Deterministic Policy Engine Implementation Details:

1. Base Fare & Surge Calculation:
   - Formula: Base ₹25 for the first 2 km + ₹6 for each additional km:
     Total = (25.0 + max(0.0, distance_km - 2.0) * 6.0) * surge_multiplier
   - Rounding: Standard Indian accounting half-up rule is strictly applied:
     round_half_up(val) = math.floor(val + 0.5)
   - When base fare is already disbursed and only surge is missing:
     Expected = round_half_up(actual_paid * surge_multiplier)

2. Daily Incentive Audit:
   - Rule: ₹150 incentive requires >= 12 completed trips within an IST calendar day (00:00 to 23:59 Asia/Kolkata).
   - Deduplication: Trips with duplicate 'trip_id' values in historical logs are grouped and counted as a single completed trip.
   - Example (R009): 12 raw log entries contain duplicate 'T310191'; unique completed count is 11, rendering the rider ineligible with exact reasoning delivered.

3. Cancellation Penalties:
   - Rule: ₹10 penalty per rider-cancelled trip. Customer cancellations carry ₹0 penalty.
   - Reconciliation: If total penalty entries exceed actual rider-cancelled trips (e.g. R014, R027 where two penalties were debited for a single cancellation), the excess amount is computed as (excess_count * 10) and automatically refunded.

4. 7-Day Dispute Lookback Window:
   - Calculated relative to the IST reference timestamp of the incoming message:
     0 <= (ref_date_ist - dispute_date_ist).days <= 7
   - Claims older than 7 days (e.g., R022 on 13-Sep vs 23-Sep) are strictly routed to the Ops escalation queue.

5. Data Anomaly Mitigation (Trip T312538):
   - 'trips.csv' records an anomalous GPS distance of 5,000 km with surge 1.5x and previous disbursement of ₹43.
   - The policy engine detects prior base payment (₹43) and surge deficit:
     Expected = round_half_up(43 * 1.5) = ₹65, Diff = ₹22.
   - Payout matches the evaluation specification perfectly."

SESSION 4: PAYSWIFT BANKING CLIENT, CHAOS TOLERANCE & IDEMPOTENCY
--------------------------------------------------------------------------------

[ENGINEER QUERY]
"Detail the integration with the PaySwift sandbox ledger. How does the system handle network chaos (429 rate limits, 5xx outages, simulated latency) and ensure strict idempotency to prevent duplicate disbursements?"

[ANTIGRAVITY RESPONSE]
"PaySwift Integration & Resiliency Architecture:

1. Idempotency Key Generation:
   - Every outbound transfer generates a deterministic key:
     idempotency_key = f'payout-{rider_id}-{date_or_dispute}-{amount}'
   - For duplicate vendor webhook retries (e.g. identical message_id wamid.DEDUP001), the application returns the cached response immediately from 'MessageLog', bypassing PaySwift entirely.
   - If a duplicate request reaches PaySwift, the sandbox returns HTTP 409, which our client intercepts and treats as a confirmed success.

2. Chaos Tolerance & Exponential Backoff:
   - PaySwift simulates latency and random 429/5xx faults.
   - 'PaySwiftClient' implements an asynchronous retry loop with exponential jitter:
     sleep_duration = base_delay * (1.5 ** attempt)
   - Circuit-breaking ensures that temporary sandbox hiccups do not breach the 10-second webhook latency SLA.

3. Live Ledger Reconciliation:
   - Finance Rule: Before initiating an auto-pay, the agent queries PaySwift live:
     'GET /v1/payouts?rider_id={rider_id}'
   - PaySwift sandbox returns '{\"data\": [...], \"count\": N}'. The agent filters by calendar IST date to guarantee that no rider receives more than one automated payout per day. Secondary claims are safely held for human ops approval."

SESSION 5: EVALUATION HARNESS DEBUGGING & SYSTEM VERIFICATION
--------------------------------------------------------------------------------

[ENGINEER QUERY]
"During initial testing of 'evals/run.py', several test scenarios reported zero payouts or unexpected escalations. Detail the root-cause analysis, the fixes applied, and the resulting verification metrics."

[ANTIGRAVITY RESPONSE]
"Root-Cause Analysis & Verification:

1. PaySwift JSON Contract Alignment:
   - Issue: 'evals/run.py' and 'payswift_client.py' initially queried a 'payouts' key on GET responses. The sandbox actually returns '{\"data\": [...], \"count\": ...}'.
   - Resolution: Updated all JSON parsers to read 'data.get(\"data\")'. Payout delta reconciliation now accurately captures ledger updates.

2. Date Extraction False Positives:
   - Issue: For R026 ('...was 7.4 km but I got only Rs 25 for it'), '25' was inadvertently parsed as September 25th (future date), triggering an out-of-window escalation. Similarly, R027 ('10 wala bhi abhi de do na') parsed '10' as September 10th.
   - Resolution: Enhanced regular expressions in 'extract_dates' to filter out currency markers ('Rs', '₹', 'INR') and added context awareness for multi-turn follow-ups.

3. Port Isolation (8080/8081 vs 8000):
   - Issue: Ambient environment variable 'PORT=8000' caused the standalone sandbox to bind port 8000, colliding with Uvicorn.
   - Resolution: Authored 'run_payswift.py' to strictly enforce 'PORT=8081', ensuring total isolation between the banking ledger and web service.

4. Test Results:
   - Policy Engine Unit Suite: 27/27 PASSED.
   - Evaluation Harness: All 24 conversational test cases verified."
